# Account: action plan

Scope: the Account / Sign In slot in the bottom nav (`src/components/BottomNav.tsx:47`) and everything behind it. That's `/auth` (`src/pages/Auth.tsx`), `/auth/callback`, `/auth/verified` and `/auth/reset-password`; `/dashboard` (`src/pages/UserDashboard.tsx`) with its overview, submit-event, events, saved-searches, advertise and settings tabs; `/profile` (`src/pages/Profile.tsx`); `/my-events` (`src/pages/ProfilePage.tsx`); and the security and privacy panels in `src/components/auth/` and `src/components/PrivacyControls.tsx`.
Inputs: the holistic audit plus five section audits (auth, dashboard, profile, security, platform). Every P0 and P1 was re-opened at its cited line on 2026-09-25. Production state comes from `scripts/db-snapshot.json` (captured 2026-08-24, ledger ends at `20260824000001`) and `docs/RLS_AUDIT.md` (static analysis of migrations, 2026-07-09). No live probe was available, so run `npm run check-schema:probe` before merging anything that names a table, column or RPC, and before any deferred item.

## Where it stands

- **Signing in with two-factor signs you straight back out.** `MFAVerificationDialog` calls `onSuccess()` and then `handleClose()`, and `handleClose` always calls `onCancel` (`MFAVerificationDialog.tsx:62-64,80-87`, same on the auto-submit path at `:101-103`). `/auth` wires `onCancel` to `handleMFACancel`, which runs `logout()` and toasts "Login Cancelled" (`Auth.tsx:314-329`). Changing your password makes it worse for the same people: `AccountCredentials.tsx:66` re-authenticates with `signInWithPassword`, which swaps the aal2 session for an aal1 one, and `AuthContext.tsx:517-537` then marks the user signed out mid-change.
- **Real addresses can't sign in or sign up.** `validateEmail` runs `containsSQLInjection`, which matches whole words like EXEC, UPDATE, DROP and UNION (`securityUtils.ts:76-86,109`). `exec@firm.com`, `jane.update@gmail.com`, `hr@drop.io` and `sam@union.edu` all fail. On sign-in the check runs inside `checkRateLimit`, so the toast says "Too Many Attempts" (`Auth.tsx:219-224`).
- **The organizer's buttons lie.** `user_submitted_events` has no user DELETE policy and its user UPDATE policy matches only `status = 'pending'` (`20250128000000_user_submitted_events.sql:33-48`, same in `RLS_AUDIT.md:677-682`). The trash button gets zero rows and no error, so it toasts "Event deleted successfully" (`UserDashboard.tsx:94-97,439-448`). Edit is offered on `needs_revision` (`:416`), the one state that asks for an edit, and fails there. Approval can't publish either: `publish_submission` concatenates a `timestamptz::text` with a time and casts it to `timestamp` (`20260920000001_publish_submission.sql:107`), which Postgres rejects. That migration isn't in the snapshot yet, so the fix can land before it's applied.
- **`/my-events` can't be trusted.** It filters and orders on the embedded `events` resource without `!inner` (`ProfilePage.tsx:55-56,118-119,161-162`). Past RSVPs come back with `events: null`, and the reminders tab dereferences `item.events.id` (`:125`). No tab reads `isError`, so every failure renders "No upcoming events". Signed out, its Sign In button goes to `/login` (`:190`), which App.tsx doesn't route (`App.tsx:446-452,639`).
- **Settings promise things nothing does.** "AI-Powered Recommendations Active" (`PreferencesSettings.tsx:186-200`) sits over controls no code reads: `recommendationAlgorithm.ts` is imported nowhere and `emailDigest` has no reader outside its own type. The weekly digest card describes a Sunday email (`EmailPreferencesCard.tsx:34,62,99`) that `get_weekly_digest_recipients` can't produce: it selects `p.home_latitude`, `p.home_longitude` and filters on `p.email_verified` (`20251110000005_add_weekly_email_digest.sql:93-98`), none of which are `profiles` columns in the snapshot. "Active sessions" reads `user_sessions` and calls `revoke_session`/`revoke_all_other_sessions` (`SessionManagementDashboard.tsx:66,90,120`), none of which exist in production, so every visit to `/profile?tab=settings` shows "Failed to Load Sessions". `useSessionTimeout` polls the same missing table every 60 seconds for every signed-in user because its queries ignore `enabled` (`useSessionTimeout.ts:134,154`). `/profile` shows literal zeros for "Events Attended" and "Reviews Written", twice (`Profile.tsx:284-291,475-482`).
- **Consent defaults disagree.** Sign-up leaves marketing email and recommendations unticked (`Auth.tsx:121-123`). `PreferencesManager` treats a missing key as `true` (`PreferencesManager.tsx:107-113`), which is every Google and Apple account, so saving an interest records a marketing opt-in nobody gave.
- **The Account tab opens on an organizer console.** At 390px a local sees a Back to Site bar, breadcrumbs, six tabs, a Free Plan / Upgrade card and four counters that are zero for nearly everyone (`UserDashboard.tsx:171-300`). Their going, saved and reminder events are on `/my-events`, which the Account tab never links to. Sign-up is about 20 controls (`Auth.tsx:985-1317`), Google and Apple appear only on the login tab (`:958-979`), and confirmation always lands on `/` (`AuthContext.tsx:768`, `AuthVerified.tsx:53`), so the page someone signed up from is gone.
- **Worth keeping:** WEB-SEC-026's aal1 hold in `AuthContext`, the server lockout through `check-login-attempt`, neutral enumeration copy, `redirectSafety.ts`'s zero-import rule, `ResetPassword`'s Zod form and `signOut({ scope: 'others' })`, trigger-written consent rows (`20260902000014`), the `ErrorState` branches on the dashboard's My Events and Advertise tabs (WEB-QA-031), `useTabState`, the `live_event_id` lookup in `useUserSubmittedEvents.ts:110-160`, the route-mocked pattern in `tests/submission-live-link.spec.ts`, and `delete-user-account`'s refusal to erase before billing is torn down.

All four tables are in the snapshot. Eventbrite shows only tickets you bought, Yelp and TripAdvisor show bookmarks with no dates, and Catch Des Moines has no accounts. Files: new `src/hooks/useMyPlans.ts`, new `src/components/account/YourWeek.tsx`, `UserDashboard.tsx`, `ProfilePage.tsx`, reading `src/lib/timezone.ts` (`centralDateOf`, `addCentralDays`). WP3.

A small `pendingAction` store in safeStorage lets the heart, save-search and watch buttons replay the tap after the account exists (their owners adopt it; see hand-offs). Competitors drop a new account on a generic home page. Files: `src/lib/redirectSafety.ts`, new `src/lib/authReturn.ts`, `Auth.tsx`, `AuthCallback.tsx`, `AuthVerified.tsx`. WP1 and WP2.
3. **A submission timeline an organizer can read.** Each row shows what happened and when, from columns the row already has: `submitted_at`, `triaged_at` and `auto_decided` ("Checked automatically 2 minutes after you submitted"), `admin_reviewed_at` and `admin_notes`, then the live listing via `events.submission_id` with its `view_count` ("Live, 214 views"). Files: `src/hooks/useUserSubmittedEvents.ts`, new `src/components/account/SubmissionsTab.tsx`. WP4.

5. **Every email switch says what it controls.** One Emails panel lists each real stream next to the store the sender reads: the weekly digest (`user_email_preferences.weekly_digest_enabled`, with "Last sent Sep 21" from `weekly_digest_log.sent_at`, which users can read), account and lifecycle mail (`communication_preferences.email_notifications`), and saved-search alerts (a link into the Search-owned tab). None of the big platforms shows you your consent history. Files: new `src/components/account/EmailStreams.tsx`, `src/hooks/useEmailPreferences.ts`, `PreferencesManager.tsx`. WP5.

## Conflicts resolved

- **Where settings live.** The holistic audit wanted `/dashboard?tab=settings`; the security audit linked to `/profile?tab=settings`. `/profile` wins: it already mounts credentials, MFA, preferences and privacy, and onboarding and `Unsubscribe.tsx` already send people there. The dashboard tab becomes a summary and a link.
- **Retire `/my-events` into the dashboard?** Not adopted. The overview shows this week; `/my-events` keeps the full lists, is protected, and stays the target of both header menus (Home WP8's files). No route or redirect is needed.
- **Delete and Edit before the policy is applied.** Both would fail against production today. Delete hides behind a flag; Edit on `needs_revision` gives way to "Resubmit a copy", which works under the current INSERT policy, so organizers get a working path in this release.
- **Severity of the digest card.** Dashboard audit P0, holistic silent. P0: it describes a weekly email the recipients RPC can't produce, to every user who opens Settings.
- **`useCampaigns` unfiltered read.** Dashboard P1, platform P2. P1: the fix is one line, and the failure would show one business another's spend.
