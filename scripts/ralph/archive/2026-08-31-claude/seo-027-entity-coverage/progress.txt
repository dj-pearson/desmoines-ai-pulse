## Codebase Patterns

Carried forward from the SEO-023 iteration (archived under
scripts/ralph/archive/2026-08-31-claude/seo-023-gsc-sync/) plus what this one found.

- **pg_cron credentials come from Vault, never from `app.settings.*`.** Supabase removed
  `app.settings.supabase_url` / `app.settings.service_role_key` and refuses
  `ALTER DATABASE|ROLE ... SET` on both, so `current_setting()` over them cannot be made to
  return a value. Use `public.app_secret('supabase_url')` /
  `public.app_secret('service_role_key')`. Gated by `node scripts/check-cron-credentials.mjs`.
- **A pg_cron job "succeeds" when `net.http_post` ENQUEUES, not when the call lands.**
  The status code lives in `net._http_response` keyed by the returned `request_id`.
- **You can query production from this environment without a service-role key.**
  `.env` holds `SUPABASE_ACCESS_TOKEN`; POST SQL to
  `https://api.supabase.com/v1/projects/wtkhfqpmcegzcbngroui/database/query` with it as a
  bearer. This runs as `postgres`, so it bypasses RLS.
- **Anon returning `[]` is not evidence a table is empty.** Any table with an
  `is_admin()`-only policy answers `[]` to the anon key whether it holds 0 rows or 15,000.
- **Parse-test a migration against production without applying it:** wrap the file in
  `BEGIN; ... ROLLBACK;` and send it through the Management API.
- **The migration ledger is 28 files behind the repo.** Never assume a committed migration
  is live - check `supabase_migrations.schema_migrations` and the object itself.
- **Bash `/tmp` and Python's `/tmp` are different directories on this machine.**

New, from SEO-027:

- **The Bash tool's heredoc collapses `\\` to `\`, even with `<<'QUOTED'`.** A Python
  patch script written that way turns `"\\n"` into a REAL NEWLINE, which silently breaks
  single-quoted JavaScript string literals (`'...\n...'` becomes an unterminated string) and
  passes `node --check` when it lands inside a template literal instead. This corrupted
  scripts/check-entity-coverage.mjs once. For any patch script containing backslashes, write
  the file with the Write tool and then run it with `python file.py`; do not pipe it through
  a heredoc.
- **Git Bash rewrites a leading `/` argument into a Windows path.** `node script.mjs /events/x`
  arrives as `C:/Program Files/Git/events/x` and puppeteer answers "Cannot navigate to invalid
  URL". Prefix the command with `MSYS_NO_PATHCONV=1` whenever you pass route paths as argv.
- **scripts/prerender.mjs RUNS on import.** `node -e "import('./scripts/prerender.mjs')"`
  launches Chromium and starts a full prerender rather than type-checking it. Use
  `node --check` to validate it.
- **Several source files have MIXED line endings.** scripts/prerender.mjs is LF in its first
  half and CRLF in its second. A patch script that anchors on a multi-line string must try
  both encodings, or it fails on one block and silently succeeds on another.
- **Throughput measured on this machine is not usable evidence.** Five identical prerender
  runs of the same 48 URLs ranged 0.28-0.84 URLs/sec. Any A/B smaller than about 2x is inside
  the noise here. Measure config effects by their MEAN over repeats, and prefer changes whose
  benefit is deterministic (ordering, coverage) over ones whose benefit is a rate.
- **Prerender throughput is bound by Supabase round-trip latency, not CPU.** An entity page
  fires 10-35 PostgREST requests in a waterfall at ~170ms base RTT. That is why raising
  PRERENDER_CONCURRENCY does nothing (measured at 6, 8, 10, 12 and 20) and why the same code
  renders ~2.75 URLs/sec on a GitHub runner and ~0.64 on Cloudflare Pages.

## 2026-08-31 - SEO-027 - Every event page and 70% of restaurant pages still ship as an SPA shell

### The premise, re-verified before changing anything

Production, `curl -A GPTBot`, 2026-08-31:

    200 | ld+json=0 | Des Moines Insider | Events, Restaurants and What to Do...  /restaurants/zombie-burger-drink-lab
    200 | ld+json=8 | Jungle Tea | Boba Tea & Desserts Cafe in Des Moines...      /restaurants/jungle-tea
    200 | ld+json=0 | Des Moines Insider | Events, Restaurants and What to Do...  /events/september-2026
    200 | ld+json=9 | Pappajohn Sculpture Park - Park/Art in Des Moines...        /attractions/pappajohn-sculpture-park

The story's premise holds: late-alphabet restaurants and all events serve the homepage shell,
front-of-order pages render correctly.

### What was implemented

- `scripts/prerender-order.mjs` (new) - the order the entity budget is spent in. Ranks every
  entity URL by measured Search Console impressions and interleaves a round-robin across
  sitemaps so no category is starved. Pure, no I/O, unit-tested.
- `scripts/prerender-priority.json` (new, generated) - 837 paths with measured impressions.
- `scripts/generate-prerender-priority.mjs` (new) + `npm run generate-prerender-priority` -
  regenerates the above from `gsc_page_performance` through the Management API. Refuses to
  overwrite a good ranking with an empty result.
- `scripts/prerender.mjs` - uses the new order; the entity budget is now ADAPTIVE, computed
  from time actually elapsed against the host's build timeout rather than a fixed 420s.
- `scripts/build-clock.mjs` (new) + `package.json` `build` - stamps `.build-start` (gitignored)
  so the budget above knows what time it is.
- `scripts/check-entity-coverage.mjs` - AC6. Adds a gate separate from the existing loose
  ratchet: the top 100 entity URLs by measured impressions must ship prerendered HTML. One or
  two lost to a render race WARN with the page named; more than 10% missing FAILS the build.
  See the tolerance rationale below - it was calibrated from a measurement, not chosen.
- `scripts/__tests__/prerender-order.test.mjs` (new) - 17 checks, picked up automatically by
  `npm run test:offline`.

### The finding this story turns on

The 2,000-line answer is one number. Joined the 2026-08-31 sitemaps to `gsc_page_performance`
over the trailing 365 days, then measured what each render order buys at the SAME coverage
production actually achieves (267 of 1,127 URLs):

    alphabetical-within-sitemap   44,965 of 93,272 impressions   48%   events 0
    prerender-order.mjs           91,257 of 93,272 impressions   98%   events 16

Same budget, same machine, same strict gate. The old order was deciding coverage by the first
letter of a slug: `/restaurants/the-pizza-bar` draws 8,089 impressions and sits 421st of 477,
`/restaurants/yard-house` 4,478 at 471st. Neither was ever going to be reached.
`/restaurants/100th-st-corner-cafe` has zero impressions and was always first.

### How it was VERIFIED

**The order, from a real build** (not modelled - this is the build's own log line):

    [prerender] render order: 837 paths ranked by measured impressions
                (gsc_page_performance, 365d window, generated 2026-08-31)
    [prerender] entity order: restaurants(477) + events(525) + pseo(14) + attractions(22)
                + playgrounds(67) + articles(18) + guides(4) interleaved, fairness every 4
    [prerender] first 267 of 1127 carry 91257/93272 measured impressions (98%);
                categories: restaurants 191, events 17, pseo 13, attractions 12,
                playgrounds 16, articles 14, guides 4

Every category is represented, which is AC4. Under the old order events was 0/525 (ALL).

**The pages themselves, on disk after that build.** The build reached only 216 entity URLs on
this machine, and the head was still complete:

    top 25 by impressions rendered: 25/25
    top 100 by impressions rendered: 100/100

including `/restaurants/the-pizza-bar` (8,089) and `/restaurants/yard-house` (4,478), the two
the old order could not reach.

**The adaptive budget, from the clean full build's own log:**

    [build-clock] build started at 2026-08-31T18:43:47.464Z
    [prerender] entities: 1127 URLs from sitemaps, budget 742s
                (278s of the host's 1200s already spent, 180s held back as margin,
                 so 742s remain)

It computed 742s where the old fixed value was 420s, from time actually elapsed. THEN IT
OVERRAN THAT DEADLINE BY 128 SECONDS - the pass reported `done in 951s` against 81s of hubs
plus a 742s budget - because renderPool checks the deadline BETWEEN routes and a route that
starts just before it still runs its own timeouts (30s navigation plus ~52s of content,
Helmet, queries-settled, skeleton and settle waits), after which six Chromium processes
close. With a 180s margin that left only 52s of the host's 20 minutes unspent, which is not
a margin. `HOST_TIMEOUT_MARGIN_SECONDS` was raised to 300 on the strength of that
measurement. This is the kind of thing a unit test over the budget arithmetic would have
reported as correct.

**The new CI gate, proved by control rather than by reading it.** Removed one rendered page:

    rm dist/restaurants/the-pizza-bar.html
    node scripts/check-entity-coverage.mjs
    -> The highest-impression entity URLs did NOT ship prerendered HTML (SEO-027)
       1 of the top 100 pages by measured Search Console impressions ...
           missing: /restaurants/the-pizza-bar
       exit 1

    (restored) -> OK All 100 highest-impression entity URLs ship prerendered HTML.

Note what that gate did on a build with only 19.1% total coverage: it PASSED. That is the
point of it - value coverage complete while total coverage is poor is the outcome this story
was aiming at, and the gate measures the thing that matters rather than the wall clock.

Two more controls on the tolerance branch, against the clean build's dist (7 of the top 100
missing): `ENTITY_COVERAGE_HEAD_TOLERANCE=5` fails and says `more than the 5 this check
tolerates`; `=0` exits 1 BEFORE the loose ratchet's message is reached, confirming the
specific gate reports ahead of the general one. Hiding scripts/prerender-priority.json makes
it warn that the head cannot be checked rather than crash or silently pass.

**The unit suite, proved by control.** Inverting the ranking comparator fails 5 checks
including "the highest-impression route renders first"; forcing `wantFair = false` fails 2
including "the fairness interleave gives the starved category a share". The suite is not
vacuous in either axis.

**That the change does not weaken the existing ratchet.** Simulated the new order against the
committed `entity-coverage-baseline.json` floors at several coverage levels:

    at 1128 / 1000 / 868 / 700 / 600   RATCHET OK
    at  400                            playgrounds 31<33, and total 400<532 already fails
    at  267                            restaurants 191<239, and total 267<532 already fails

The old order guaranteed the small sitemaps were complete because they rendered first, so this
was a real risk. It does not bite: below ~600 the TOTAL floor fires first, so no group floor
can fail a build the total would have passed. CI's historical range is 868-1136.

Quality: `npm run type-check` clean. `npm run lint` 0 errors, 3,670 warnings (unchanged
pre-existing count). `npm run test:offline` 18/18. Invisible-character and smart-punctuation
scans clean on all new and changed files.

### Corrections to the story's own premises

- **AC2 is wrong that concurrency is the lever.** It says "Raising PRERENDER_CONCURRENCY, or
  rendering incrementally, is the lever." Measured over 48 URLs on identical input:

        concurrency  6   0.46/s      concurrency 12   0.47/s
        concurrency  8   0.28/s      concurrency 20   0.45/s, and 17 of 48 FAILED the strict gate

  Throughput is flat from 6 to 20 and quality collapses at 20. The bottleneck is Supabase
  round-trip latency - an entity page fires 10-35 PostgREST requests in a waterfall at ~170ms
  base RTT, traced per request - so the workers are idle, not saturated. More of them does not
  help. `PRERENDER_CONCURRENCY` is left at 6 and the misleading remediation advice in the
  over-budget warning has been corrected to point at the order instead.

- **Blocking images during capture buys nothing.** Tested because it looked like the obvious
  win. Aborting image/font/media requests changes the output - `/restaurants/zombie-burger-drink-lab`
  lost a real `<img>` to an `onError` fallback (EventCard.tsx:124), 10 imgs to 9. Serving a 1x1
  stub GIF instead keeps the HTML BYTE-IDENTICAL (212,109 == 212,109 and 209,817 == 209,817 on
  two sampled pages) - but the mean rate over repeats was 0.486/s stubbed against 0.49/s plain.
  The effect is zero, so it is NOT shipped. Recording it so nobody re-derives it.

- **AC3's incremental prerendering is not the right answer, and the reason is not effort.**
  Two blockers and one disappearance:
  (1) prerendered HTML embeds content-hashed asset URLs (`/assets/index-DVQRdZUy.js`), so
      reusing a page from an earlier build ships a dead script tag and the SPA never boots for
      real users. Safe reuse means re-splicing every cached fragment onto the fresh shell.
  (2) Cloudflare Pages git builds have no persistent cache to hold the fragments in.
  (3) With the ordering fix the value case collapses: the 860 URLs a full pass would add hold
      2% of measured impressions. Building a cross-build cache to chase 2% is the wrong trade.
  A full pass still does not fit the 20-minute limit. That is now a coverage fact rather than a
  visibility fact.

- **"Events is the highest-value module on the site" does not survive the data.** The story
  quotes docs/seo-plan-2026-08-28.md on that. Over the trailing 365 days, restaurant entity
  URLs drew 87,371 impressions and event URLs drew 632 - a 138x gap, with 30 of 525 event URLs
  drawing anything at all. Events are still given a guaranteed share (AC4) and the reason is
  freshness, not measured value: 495 of 525 event URLs are future-dated, so ranking alone would
  make "never rendered" self-fulfilling for the whole category.

### A real defect this surfaced, which is NOT fixed here

The clean full build refused SEVEN of the top 100 pages by impressions, including
`/restaurants/bonchon` - the site's single highest-impression URL at 10,473 over 365 days:

    [prerender] route /restaurants/bonchon failed: strict gate: page did not render as
                itself (no canonical) - refusing to publish it
    ... same for fairway-franks-bar-grill, 100th-st-corner-cafe, saffron-indian-cuisine,
        dublin-bay-irish-pub-grill, mojitos-mexican-grill; el-fogon timed out navigating

The same build reported those pages under both `captured WITHOUT a queries-settled signal`
and `captured with a skeleton still mounted`, and an earlier idle run of the same tree
rendered 100 of 100. So it is a load-sensitive race, not broken data, and the strict gate is
behaving correctly by refusing them. Traced with per-request instrumentation:
`/restaurants/100th-st-corner-cafe` fires six queries after its first resolves, including
`rpc/get_rotated_restaurants` and a DUPLICATE of the related-restaurants query, and its
queries-settled signal lands at 6.2s against a 10s timeout - so under load it misses, and
Helmet has not committed the canonical when the capture runs.

Not fixed here because the fix is app-side (a detail page's canonical should not depend on
its data having arrived) and this story is a budget-and-ordering story. It is why the head
gate warns rather than blocks below 10%, and the warning names the pages so it does not go
quiet. Worth its own story.

### What could NOT be verified from this environment

- **The post-deploy `curl -A GPTBot` in AC5.** This branch is not deployed. What was verified
  instead is the artifact the deploy would serve: the rendered files on disk, sampled at the
  END of the ranking as well as the front. Re-run the AC5 probe against production after merge -
  `/restaurants/the-pizza-bar` and `/restaurants/yard-house` are the two that should flip from
  the homepage title to their own.
- **The rate on the Cloudflare Pages build host.** Everything here was measured locally
  (0.28-0.84/s) and against the recorded production figure (267 in 420s = 0.64/s). The adaptive
  budget was chosen to be safe under BOTH: it can only shrink when a build is already running
  late and only grow when there is measured headroom, so it is strictly safer than the fixed
  420s it replaces. The first Cloudflare build after merge is what confirms the real budget;
  its `[prerender] entities: ... budget Ns (...)` line states the arithmetic it used.
- **`entity-coverage-baseline.json` was deliberately NOT re-baselined.** Its 1,064 total is
  calibrated to a GitHub runner, which renders far faster than this machine; a local build
  reaching 216 cannot meet it and `check-entity-coverage` fails here on the total ratchet for
  that pre-existing reason. Re-baselining from a local build would bank a 5x regression as the
  new normal. It needs a CI run to move, and that is a human's call.

### Learnings for future iterations

- **The cheapest fix on this PRD so far was not a fix to the renderer.** Nothing about the
  prerenderer's speed, gate or budget changed the number that matters; re-ordering a list did.
  When a pass is losing a race it cannot win, ask what it should spend the time it HAS on
  before asking for more time.
- **A biased sample produced the wrong conclusion twice on this story.** The original audit
  sampled three URLs from the front of the render order and concluded entity prerendering
  worked. Sampling the front is sampling the thing the budget guarantees. Sample the END.
- **`gsc_page_performance` is now the tie-breaker for anything that has to be prioritised.**
  SEO-023 made it real (15,239 rows over 361 days) and this is the first story to spend it.
  Query it before ranking anything by intuition - it disagreed with the committed plan about
  events, and it disagreed with alphabetical order about 55% of restaurant impressions.
- **The `floors` mechanism in entity-coverage-baseline.json is load-bearing and easy to break
  from a distance.** Changing the render ORDER changes which groups are complete at partial
  coverage. Any future change to prerender-order.mjs should re-run the floor simulation in this
  entry before assuming the ratchet still passes.
